# Contributing

Thanks for helping improve the HPC@ISR-Lisboa/LARSyS repositories. This is organization-wide starter guidance. If a repository has its own instructions, follow those instructions as well.

## Before opening an issue or pull request

- Read the repository's `AGENTS.md`, `README.md`, and task-specific guidance. For shared operations, use the [repository operations guidance](governance/REPOSITORY_OPERATIONS.md).
- Search existing issues, pull requests, and Discussions before creating another record. Use an issue for actionable work and a Discussion for a genuine open question or coordination topic. Do not create placeholder records.
- Use concise, descriptive Title Case titles without workflow prefixes or ticket identifiers unless the repository explicitly requires another format.
- Record verified evidence, acceptance checks, dependencies, and the difference between an estimate and a confirmed commitment.
- Assign a responsible owner or reviewer only when the responsibility is supported by evidence. If ownership is unclear, state the decision needed instead of guessing.

## Pull requests

- Follow the repository's approved branch and review workflow; do not bypass protections or rewrite shared history.
- Use the pull request template. Describe the change, related work, checks actually run, limitations, and approvals still needed.
- Keep a pull request in draft while it is incomplete or not ready for independent review.
- Keep implementation changes in the repository that owns the code or configuration. Link to authoritative material instead of copying it into another repository.

## Information boundaries

- Do not commit credentials, private keys, tokens, personal data, or restricted operational details.
- Keep public guidance suitable for public readers. Put private administrator documentation, deployable automation, workload examples, and restricted coordination records in their designated repositories.
- Never describe a proposed control as deployed or a test as passed without the corresponding evidence.

## Review and completion

Use existing labels and milestones where they fit. A milestone target is an estimate unless explicitly approved as a commitment. If GitHub does not expose a native due-date or dependency field, state the estimate or dependency in the issue body and do not claim the native field was set.

For repository-specific contact and support routes, use that repository's documentation or the [organization profile](profile/README.md).
